# 製作經驗補記：截斷 runtime 下的安全修訂門檻

## 本階段狀態與證據

AMT-01～08 是本輪最前面的未完成內容工作，但 runtime 讀取回傳在 A03 中途截斷，檔案介面只有整檔覆寫，沒有本機程式執行、parser／ID selector、暫存檔原子替換或精確 patch。故本輪保持 A03／A04／A05 章稿與 `site/game-data.js` 原狀，避免只修章稿或以截斷資料覆蓋遊戲資料。固定 `routes`、`game-data`、`shells` 均通過；它們不證明 AMT 敘事已修，也不提供安全寫檔能力。具體紀錄與恢復條件見 `reviews/amt-runtime-edit-blocker.md`。

## 可複用方法與適用範圍

1. **先判斷資料完整性，再決定寫入策略。** 若讀取工具可能截斷，輸出只可用於讀取已完整涵蓋的局部上下文，不可重建或整檔覆寫大型 runtime。適用於超長 JavaScript 資料、JSON、設定檔與生成資料。
2. **以語意 ID 做局部更新，並要求唯一性。** 安全流程應完整 parse、驗證章節 ID 唯一、精確修改單節，再完整 parse 暫存結果及確認非目標節未變；任何前置條件失敗就中止。適用於章節資料庫、路由表和大型結構化內容。
3. **先寫同目錄暫存檔，驗證後原子替換。** 此流程可避免半寫入或格式錯誤造成 runtime 損壞；沒有能實際執行並驗證該流程的工具時，不能把手工重寫聲稱為等價方案。適用於任何重要 runtime／設定檔更新。
4. **正文與 runtime 是成對交付。** 一方無法安全修改時，不要單獨發布另一方製造版本分歧；可記錄修稿基準、阻塞原因與恢復程序，保持兩份內容不動。適用於 Markdown 劇本與遊戲資料同步、翻譯文案與應用資源同步。
5. **複合 stage-all 工具不等同可檢視 Git 狀態。** 若無法確認分支、status 和 diff，且提交工具會 stage 所有非忽略變更，就不應冒險把既有未提交工作一起提交。適用於受限 Git 代理、共用工作目錄及使用者要求保留現有變更的情況。
6. **驗證與修復必須分開報告。** 現有 validators 通過只描述當前資料符合其檢查項；修訂工作仍需有同步變更和審校依據。適用於所有有自動 CI 的內容專案。
