# 製作經驗與可複用流程

這份文件記錄本企劃迭代中已驗證或值得沿用的做法。每次繼續工作時先讀本檔與 `plan.md`，做完一個階段後補上新經驗，並推回計畫與 Git。

## 適用範圍

可用於本作的長篇互動小說、Galgame 腳本、路線規劃、圖像製作與 GitHub Pages 發布；其中分支記錄、素材一致性和部署流程也可用於其他文字冒險或個人企劃。

## 迭代工作流程

1. 先查看 `knowledge/plan.md`、本檔、`knowledge/decision.md`、工作目錄及 Git 狀態，確認實際進度，不依賴舊對話猜測狀態。
2. 依路線圖選出目前最靠前、可獨立完成的階段。需要人類偏好的選擇時，先列選項與推薦至 `decision.md`，同時繼續所有不受該選擇阻塞的工作。
3. 把穩定設定放在故事聖經，把尚未決定的內容留在決策紀錄；不要把臨時腦洞當成既定正史。
4. 正文每節以 Galgame 結構呈現：背景、音樂／音效、角色立繪狀態、對話與旁白、選項及其後果。每節標識章節／場景 ID，方便追蹤素材和分支。
5. 寫完分支後，記錄玩家選擇、路線旗標、收束點及仍待處理的分支，不依靠聊天記憶維護連續性。
6. 依每節實際需要安排圖像，優先建立可重用的背景、角色立繪和表情差分；事件 CG 用於情緒或劇情的重要節點。素材都要保存於 repo，並在素材清冊記錄路徑和用途。
7. 每個階段完成後更新計畫勾選、回流新經驗、提交 Git 並推送。若工作流已觸發，檢查部署狀態與 Pages 畫面再宣告發布完成。
8. 每階段用一至兩句中文向使用者回報後繼續推進，不把狀態回報當成完成工作。

## 寫作與篇幅經驗

- 作品目標是 80,000～150,000 字；全篇約 3,000～5,000 句旁白／對話；每節約 2,500～4,000 字、80～130 句、8～12 分鐘閱讀。
- 「字」預設按中文字元／可見文字計算，而非 token；Galgame 控制標記、空行與選項標籤不納入正文篇幅。每節仍須記錄實際估算與句數，避免總規模失控。
- 每節需有一個情緒或關係上的小進展；選項可以改變互動方式或局部事件，主線資訊不應因單一選項而遺失。
- 以使用者提供的黃昏辦公室段落作為氛圍參考：光線、紙張、公務壓力、陽奈動作與克制語氣彼此呼應。避免照抄同一組比喻，後續以具體感官細節延伸。

## 視覺素材經驗

- 先從場景底圖開始，保持底圖無人物、無對話框和無文字，方便角色立繪疊加及跨場景重用。
- 立繪與差分須維持輪廓、服裝、髮色、配件、視線方向及透明底一致；每次生圖保存 prompt、版本和用途。
- 全篇圖像採同一風格基準；色彩、光線及鏡頭語言配合場景情緒，不在單張圖中混用媒材。
- 優先使用內建圖像生成能力。若當前工作階段沒有該工具，不要默默切換需要 API key 的 CLI；記下缺口並先完成文字規格及其他不受阻工作。

## 專案與發布經驗

- 純靜態網站可將發布來源設為 GitHub Actions，使用 Pages artifact 流程部署 `site/`，其他知識文件則留在 repo 根目錄。
- GitHub Actions 第一次觸發若早於 Pages 設定，`configure-pages` 會因找不到 Pages site 而失敗；先在 Settings → Pages 選擇 GitHub Actions，再重新執行 workflow。
- 頁面更新以推送到 `main` 自動發布；每次推送後留意最新 run，成功後再查公開 URL 是否呈現新版本。
- 公開頁面是企劃展示，不等於已完成遊戲；README 和網站需清楚標示當前階段、同人性質與未完成內容。

## 經驗紀錄

### 2026-11-19：專案啟動與 Pages 初次部署

- **觀察：** 開始時工作區只有計畫文件，故事設定與經驗檔缺失；GitHub Pages workflow 在 Pages source 尚未設定時第一次失敗。選擇 GitHub Actions 後重新執行，網站成功發布。
- **做法：** 以網站展示企劃而非假裝遊戲已完成；將 workflow artifact 指向 `site/`；記錄 GitHub Pages 設定步驟，避免把首次失敗誤判成靜態頁或 Actions 腳本錯誤。
- **未來可用於：** 新 repo 的 GitHub Pages 靜態網站、互動小說企劃的初始目錄設計，以及日後任何依 Actions 發布的個人頁面。

### 2026-11-19：長篇互動敘事的工作基準

- **觀察：** 使用者已有明確字數、單節閱讀時間、分支形式與 Galgame 視覺期待，但玩家關係、時間線與具體路線仍未定。
- **做法：** 把量化規格、穩定的風格參考與待決選項拆開管理；不讓未知的關係設定阻塞文檔、分支格式和素材清冊等可預備工作。
- **未來可用於：** 本作所有章節、角色路線、配圖製作及其他需要分批完成的長篇互動文字企劃。

### 2026-11-19：分支長篇篇幅估算

- **觀察：** 單節字數目標適用於實際交付的小節，而不同分支並非每位讀者都會閱讀；若只按單一路徑或把共通段重複計算，會低估或高估全篇實際工作量。
- **做法：** 以所有唯一正文段落計入全篇目標，共通段落只計一次；另保留每條遊玩路徑的閱讀量估算。先用四幕＋共通主線和旗標分歧建立容量，再依章節卡調整。
- **未來可用於：** 有分歧路線的 Galgame、互動小說、劇本式遊戲或任何需估算互斥內容工作量的長篇企劃。

### 2026-11-19：將長篇主線拆為章節卡

- **觀察：** 長篇架構若只停留在幕次，容易重複日常事件，也難估算分支容量、素材需求和每節情緒功能。
- **做法：** 每節卡明列目的、情緒變化、旗標、會合點和素材；先以共通主幹＋短分歧估算容量，再把路線篇幅當作唯一正文統計。
- **未來可用於：** 把分幕大綱轉成可連載的 Galgame 節奏、追蹤支線會合和配圖進度，並在角色細節待核對時先用職務描述避免寫錯正史。

### 2026-11-19：先交付 P01 再處理分支

- **觀察：** 序章若同時等待所有分支、圖像和官方資料核對，文字交付會停滯在規劃階段。
- **做法：** 先完成 P01 共通場景與 A/B/C 分支骨架，把旗標、會合點和下一節選擇寫入章節檔；無人物立繪或具名配角時，不靠猜測補設正史。
- **未來可用於：** 後續逐節創作、分支旗標驗證及章節卡與正文的雙向回流。

### 2026-11-19：序章三線分支與共通會合

- **觀察：** 底層分歧需要保留差異，但不能讓選擇成為永久且互不相容的主線。
- **做法：** P02 分別記錄休息、分工、日常三條旗標；P03 依旗標回收對話，再以共同約定進入第一幕。
- **未來可用於：** 旗標條件回收、分支對話收束與後續章節讀取不同陪伴方式。

### 2026-11-19：第一幕入口以小規模常態變化開始

- **觀察：** 第一幕不宜用重大危機取代陽奈日常習慣，否則會讓她的核心問題突然改變而失去連續感。
- **做法：** A01 先讓學生時期的陽奈在熟悉公務中保留小空位，以三種陪伴方式呈現不同進展，不宣告戀愛。
- **未來可用於：** 第一幕所有章節、校園篇角色一致性、以小事件累積後續信任旗標。

### 2026-11-19：離線續作需區分主機、repo 與雲端權限

- **觀察：** 主機聊天、GitHub Pages 部署和雲端 Automation 是三條不同的執行鏈；修改檔案再 push 只解決線上部署，不代表離線時仍會有 AI 繼續執行。
- **做法：** 公開 repo 若不支援 Automations，先記錄可行替代方案與實際前置條件，不假裝建立成功。需要私有化時，主機不可代替 GitHub 網頁設定；若環境權限不足，把精確步驟與狀態寫入 decision record。
- **未來可用於：** 需要 24 小時或離線續作的個人企劃、GitHub Pages 長期迭代，以及任何需區分 repo 可見性、workflow 部署與雲端代理執行權限的專案。

- **決定回流：** D-05 已由使用者放棄，不再將私有化或雲端 Automation 列為專案阻塞；保持 repo 公開與既有 Pages 部署，持續聚焦故事、分支、圖像規格與完整稿件。

### 2026-11-19：A02 以退件公務呈現責任與求助距離

- **觀察：** 直接把陽奈寫成拒絕休息或拒絕分工會過度簡化其習慣；更合適的衝突是讓責任、規則與無效重做分開辨識。
- **做法：** 以同一份退件公務作為共通事件，休息線建立可被打斷的界線，分工線只交出核對而保留決策，回顧線將無效重做轉為可重複規則；最後都收束到區分「只能由我判斷」與「可以請人協助」。
- **未來可用於：** 第一幕後續公務章節、第二幕團隊分工、任何需要讓陽奈學習求助而不削弱主導權的場景。

### 2026-11-19：A03 用界線清單承接分工與主導權

- **觀察：** 單純讓陽奈「交出工作」容易削弱其決策角色；分工需要同時保留必要判斷、交付可核對內容與等待完整資訊的規則。
- **做法：** A03 將事項拆成決策、確認、可交付與暫不處理四種界線，三個分支分別補強休息、分工或日常選擇，不改變陽奈的最終決策權。
- **未來可用於：** 第二幕的任務分類、團隊流程與陽奈主動求助章節，以及需要避免「學會休息」變成被動服從的對話。

### 2026-11-19：A04 以臨時協助測試責任來源

- **觀察：** 把協助直接寫成陽奈新增的工作量會讓角色只看見負擔；保留目的地、交付者與下一步，才能讓協助成為可靠分工的一部分。
- **做法：** A04 使用不具名學生避免未核對原作設定，以三種選項測試暫存公務、協助學生列出步驟與共同確認目的地，最後回收為「需要協助時先停下確認」。
- **未來可用於：** 第一幕日常事件、第二幕團隊協作及任何不指定原作配角的校園場景。

### 2026-11-19：A05 將休息寫成預留而非補償

- **觀察：** 把休息設為工作完成後的獎勵會讓它永遠排在最後；陽奈能接受的是把休息列為預先保留的一段時間，但仍允許後續波動。
- **做法：** A05 用錯過原定十分鐘作為低強度衝突，三條分支分別強化現在休息、交付確認與單純離開，共通收束於承認並預留而非要求完美執行。
- **未來可用於：** 第一幕收束、第二幕自主管理休息，以及需要呈現反覆失敗但持續小幅改善的章節。

### 2026-11-19：A06 用可反覆的約定收束第一幕

- **觀察：** 第一幕收束不宜把陽奈寫成已完全改善；更可靠的收束是保留可重複的日常約定，允許急件或忘記休息。
- **做法：** A06 設置 `daily_checkin`，讓三條分支分別收束到先休息、先確認分工或先做普通事；共通結果是明日仍可重新確認，不取消所有工作。
- **未來可用於：** 幕間收束、第二幕壓力累積、任何需要讓角色承諾小幅改變而不宣告性格徹底轉變的章節。

### 2026-11-19：B01 用例行工作量建立第二幕壓力

- **觀察：** 第二幕不應靠大型突發危機突然升壓；例行事項變多、時間點重疊且可預見地增加，會更自然地檢驗陽奈是否仍保留分工習慣。
- **做法：** B01 讓三項任務同時出現，但只在選項中決定先休息、交付或重新排列時間，不否定公務本身。
- **未來可用於：** 第二幕所有逐步累積壓力的章節，以及避免危機突然改變角色核心習慣的寫法。
