# 第二幕收束至第三幕入口 B07→B08→C01：休息承諾與回查交接審校

## 範圍與限制

- 完整閱讀 `story/chapters/B07.md`、`B08.md`、`C01.md`，核對兩組章間連接及 B08、C01 的 A／B／C 分支共通回收假設。這是人工稿件審校，不是瀏覽器通關，也不是全部旗標歷史的窮舉。
- 三個固定 validators 通過；它們驗證 runtime／章稿同步和資料結構，不會判斷本文件所記的時段、承諾或任務語義。
- 本輪只記錄問題與推薦，未修改故事稿、runtime、旗標、存檔、素材或遊戲功能；不得將本審校視為修稿完成。

## 核對結果與待釐清事項

### BCA-01｜B07→B08 的隔日與熱飲便條延續基本成立

B08 metadata 與首段明定「隔日放學後」，因此 B07 的「明天見」及「明天先看回查資料」有時間落點。B07 留下「喝完熱飲，不重新開檔」的便條，B08 說明今天沒有熱飲並另寫新的十分鐘安排；它把便條當作前一日的提醒，而非假設今日又喝過熱飲，沒有直接矛盾。

**建議：** 保留目前時間設定。修訂其他項目時不要把 B08 改寫成 B07 同一晚，也不要暗示 B07 的熱飲延續成 B08 的休息內容。

### BCA-02｜B07「明天第一步」的回查結果未在 B08 明確結案（待釐清）

B07 收尾把翌日第一步說成「先看回查資料，再決定今天是否需要改流程」。B08 開場只說今天第一輪確認完成、工作比昨天少，沒有明指該回查資料已到、已確認或仍在等待；後文的新通知是普通資料補充，也不能確定就是 B07 的設備回查。讀者可能把「第一輪確認完成」理解為該回查已完成，也可能認為承諾未回收。

**推薦：** 在 B08 開場用一句短句明確標示回查狀態：若資料已到，說明只確認到可判斷程度並保留例外；若尚未到，將它列為等待項而非已完成。不要把新通知直接認作設備資料，除非稿件明確建立兩者為同一事件。這是最小的狀態補足，不需新增危機或長段公務。

### BCA-03｜B08 三分支的休息方式沒有被共通段錯誤假設（通過）

- A 在走廊散步並買飲料；共通段沒有要求每條路徑都離開辦公室或喝飲料。
- B 留在桌邊喝水並寫「想到，不等於現在要做」；共通段只回收不查看手機的共同結果，沒有引用這張分支便條。
- C 寫下明日第一步並放在文件夾上方；共通段沒有假設所有路徑都寫過該句。

三條分支共同具備把手機收進抽屜、先不查看普通通知的前提，因此 17:10–17:20 共通休息成立。分支差異保留，沒有看到以單一路徑物件冒充共通狀態的問題。

### BCA-04｜B08 C 的「明日第一步」未在 C01 明確回收（待釐清，低嚴重度）

C 分支留下「先看設備回查資料，再判斷是否需要改流程」並放在文件夾最上方。C01 次日開始熟悉的設備例行檢查，確實出現兩個需要回查的例外，但沒有確認這是否承接前一日的第一步。A／B 分支沒有這張便條，故不能在 C01 共通段直接假設所有玩家都看過或使用它。

**推薦：** 若兩節的設備資料屬同一批，在 C01 的條件對話或只限 C 路徑的回應中回收便條；若只是例行任務重複，補一個簡短來源／日期區別，避免讀者誤認同一批資料被隔日重新檢查。若無法確認資料相同，先保留為待釐清，不要在共通段宣稱 C 分支成果已普遍發生。

### BCA-05｜C01 的設備例外與 B07 回查項目可能重複，也可能是新一輪任務（待釐清）

B07 預告明早回查設備資料；B08 是隔日放學後，C01 再進入設備例行任務並出現「日期不完整」與「數值不同」兩項資料。稿件沒有明確說明 B07 的回查何時完成、C01 是否同一項設備或新一週例行檢查。僅憑「設備」一詞不能判定重複，但連續章節都聚焦回查，容易讓人混淆資料批次。

**推薦：** 優先沿用 BCA-02 的最小狀態句，並在 C01 用「本週新一輪」或「前次回查完成後」等簡短時間／來源錨點區分批次；只有在兩節確定為同一資料時才明確承接，不額外創造新的未記錄結果。需和 BCT-01～02 的待修基準一併處理，避免重複或相互矛盾地指定設備回查狀態。

### BCA-06｜C01 的共同任務流程沒有依賴單一 B08 分支（通過）

C01 以「昨天留下必要條件」開場，這是三種 B08 分支皆成立的共通層級：三線都經歷了不把每一個工作步驟全部收回、並留下可重用安排。C01 的兩種記錄格式、來源欄位及例外條件均在 C01 當日新呈現，不要求玩家必須在 B08 選 A／B／C。B08 C 的明日第一步雖可能與 C01 設備任務相連，這只影響可選的回憶細節，不推翻共通入口。

**建議：** 保持 C01 共通主線不依賴 B08 C；如要回收便條，使用條件台詞或分支提示，不改成所有路徑都曾寫下該句。

### BCA-07｜C01 共通段的完成結果與分支承諾大致相容

C01 A 將第一輪交給同伴，B 一起走一區後交接，C 先理解整理方式；共同入口都支持同伴完成其餘第一輪、陽奈處理例外。共通段呈現日期來源補齊、設備差異經確認及不重做整份資料，未引用 A 的「只看三類例外」、B 的特定路徑或 C 的特定筆記。A／B／C 的方式差異仍可辨識。

**注意：** C01 文內在「第一輪檢查在下午前完成」後，才說陽奈看到預留休息還剩三分鐘，之後同伴交回回查結果。時間順序可解讀為跨越休息時段的午後流程，沒有足夠證據判定矛盾；若後續重排場次，需保持「休息尚餘三分鐘」與同伴回報的先後關係，不要寫成休息已被公務挪用。

## 修稿順序建議

1. 先解決 BCT-01／BCT-02 與 BCA-02：確定 B07 設備回查的責任、時點、數量與結果，再更新 B08 的隔日狀態。
2. 再決定 C01 是否承接同一批設備資料；如是，寫明承接；如否，標示新一輪來源／日期。
3. B08 C 的便條只在該分支或條件回憶中回收，不把它帶進 C01 所有路徑的共通正文。
4. 修改需同步 Markdown 與 runtime；審校通過、固定 validator 通過都不代表故事問題已修復。

## 固定驗證與限制

本次 `game-data`、`routes`、`shells` 固定 validators 均通過。routes 對 B08／C01 分別核對 140／150 條對話 tuple、分段及其配置的選項同步；game-data 輸出 33 章、99 選項／分支、21 條件組及 33 個背景映射；shells 核對正式／試玩頁各 37 個必要 DOM ID。

上述檢查不驗證 B07 的回查在故事中是否完成、不比較設備資料批次、不替代十八種以上的瀏覽器路徑測試或全篇敘事 QA。沒有修改正文或 runtime，沒有重新統計全篇篇幅，也沒有查詢 GitHub Actions／Pages。`.env`、原圖及原有美術檔案未修改。
